## 1. リポジトリ役割分担

| リポジトリ | 役割 | コミット対象 |
|-----------|------|------------|
| **Gitea**（ローカル） | 全データのバックアップ保管庫・開発の中心 | コード・ドキュメント・仕様書・全ファイル |
| **GitHub** | CI/CD・リリース専用 | コードのみ（内部ディレクトリを除く） |

```
Gitea
├── main / develop  ─── コードのみ ──→ GitHub Actions（CI・リリース）
└── gitea-private   ─── 内部ディレクトリのみ（GitHub へは同期しない）
```

### gitea-private ブランチで管理するもの

| ディレクトリ | 用途 |
|------------|------|
| `docs/` | 仕様書・設計書・タスク管理 |
| `openspec/` | 改修仕様・変更管理 |
| `.claude/` | Claude Code コマンド・スキル設定 |
| `.devcontainer/` | 開発コンテナ設定 |
| `.gitea/` | Gitea Actions ワークフロー |

### main / develop に含めるもの（GitHub へ同期される）

- `src/`（ソースコード）
- `Cargo.toml` / `Cargo.lock` / `build.rs`
- `README.md`（リポジトリ説明）
- `.github/workflows/`（GitHub Actions ワークフロー）
- `scripts/`（開発補助スクリプト）

## 2. gitea-private ブランチの運用

### 2.1 開発着手時（develop に切り替えたとき）

`docs/` 等の内部ディレクトリは `main`/`develop` の `.gitignore` に登録されているため、  
ブランチ切り替え後に以下のスクリプトで `gitea-private` から取得する。

```bash
git checkout develop
./scripts/pull-private.sh
```

このスクリプトは `gitea-private` ブランチの最新を fetch し、  
内部ディレクトリ（`docs/` `openspec/` `.claude/` `.devcontainer/` `.gitea/`）を  
作業ディレクトリに展開する。ファイルはアンステージ状態（git には追跡されない）。

### 2.2 内部ディレクトリを更新したとき

```bash
git checkout gitea-private

# 変更を確認・コミット
git add docs/ openspec/ .claude/ .devcontainer/ .gitea/
git commit -m "docs: ..."
git push gitea gitea-private

# 作業ブランチに戻る
git checkout develop
```

## 4. 開発環境セットアップ

### 4.1 devcontainer（推奨）

リポジトリには `.devcontainer/` が含まれており、VS Code で **Reopen in Container** するだけで開発環境が構築される。

**初回のみ: ホスト側で環境変数を設定する**

Windows（PowerShell）:
```powershell
[System.Environment]::SetEnvironmentVariable("GITEA_TOKEN", "<アクセストークン>", "User")
[System.Environment]::SetEnvironmentVariable("GITEA_USER", "youmei", "User")
# GITEA_URL は省略可（デフォルト: http://unas-250509.local:3000）
```

設定後にコンテナを **Rebuild** すると `tea` ログインと `git` 認証が自動で構成される。

### 4.2 Gitea CLI（tea）の手動セットアップ

devcontainer の自動設定が使えない場合（コンテナ外・SSH 環境など）は `tea login add` で対話的に設定する。

```
$ tea login add
 URL of Gitea instance:  http://unas-250509.local:3000
 Name of new Login:      unas-250509.local:3000
 Login with:             oauth
 Allow Insecure connections: true
```

ブラウザが開き OAuth 認証が完了すると `tea` コマンドが使えるようになる。

```bash
# ログイン確認
tea login list

# リポジトリ一覧
tea repo list
```

### 4.3 git push の認証

`tea login add` 完了後、git の認証情報を登録する:

```bash
git config --global credential.helper store
echo "http://<ユーザー名>:<トークン>@unas-250509.local:3000" >> ~/.git-credentials
```

## 5. ドキュメント除外の仕組み（旧方式・参考）

Gitea から GitHub へのプッシュは Gitea Actions が行う。  
`docs/` ディレクトリを除いたクリーンなツリーを生成して GitHub へ force-push する。

```yaml
# .gitea/workflows/sync-github.yml

name: Sync to GitHub

on:
  push:
    branches:
      - main
      - develop

jobs:
  sync:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Remove docs and push to GitHub
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_MIRROR_TOKEN }}
          GITHUB_REPO: ${{ secrets.GITHUB_REPO_URL }}
        run: |
          git config user.email "ci@aipulsehub.local"
          git config user.name "AiPulseHub CI"

          # Gitea 専用ディレクトリを除いたコミットを作成して GitHub へ push
          git filter-branch --force --index-filter \
            'git rm -r --cached --ignore-unmatch docs/ openspec/ .claude/' \
            HEAD

          git remote add github "https://x-access-token:${GITHUB_TOKEN}@${GITHUB_REPO}"
          git push github HEAD:${GITHUB_REF_NAME} --force
```

> **補足**: `git filter-branch` の代わりに `git-filter-repo` を使うとより高速・安全に除外できる。

## 6. ブランチ戦略（Git Flow）

```
main
 │  ← リリースタグ（v1.0.0）
 │
 ├─ release/v1.0.0  ─────────────────┐
 │                                    │
develop ◄───────────────────────────┘ (マージバック)
 │
 ├─ feature/add-xxx
 ├─ feature/fix-yyy
 └─ hotfix/v1.0.1  ─── main へ直接マージ（緊急修正時）
```

### ブランチ一覧

| ブランチ | 命名規則 | 役割 |
|---------|---------|------|
| `main` | 固定 | リリース済みの安定版。タグが打たれたコミットのみ存在する |
| `develop` | 固定 | 開発の統合ブランチ。次リリースの最新状態 |
| `feature/*` | `feature/{内容}` | 機能開発・バグ修正の作業ブランチ |
| `release/*` | `release/v{version}` | リリース準備ブランチ。バージョン番号を確定させる |
| `hotfix/*` | `hotfix/v{version}` | 本番の緊急修正。`main` から分岐し `main` へ直接マージ |

## 7. 開発フロー

### 7.1 通常の機能開発

```
1. develop から feature ブランチを切る
   git checkout -b feature/xxx develop

2. 実装・コミット（Gitea へ push）

3. develop へ PR を作成・マージ

4. feature ブランチを削除
```

### 7.2 リリース手順

> **ルール**: 1つの release ブランチに含める feature は**必ず1つ**とする。

```
1. develop から release ブランチを切る
   git checkout -b release/v1.2.0 develop

2. release ブランチ上でバージョンと CHANGELOG を更新
   - Cargo.toml の "version" を "1.2.0" に変更
   - CHANGELOG.md の [Unreleased] セクションを [1.2.0] - YYYY-MM-DD に書き換え
   - コミット: "chore: release v1.2.0"

3. 動作確認・最終調整（バグ修正のみ。新機能追加は不可）

4. main へマージ
   git checkout main
   git merge --no-ff release/v1.2.0

5. バージョンタグを打つ（→ GitHub Actions がトリガーされる）
   git tag v1.2.0
   git push origin main --tags   # Gitea へ push
   # Gitea Actions が GitHub へ同期 → GitHub Actions がビルド・リリースを実行

6. develop へマージバック
   git checkout develop
   git merge --no-ff release/v1.2.0

7. release ブランチを削除
   git branch -d release/v1.2.0
```

### 7.3 緊急修正（hotfix）

```
1. main から hotfix ブランチを切る
   git checkout -b hotfix/v1.2.1 main

2. 修正・コミット

3. Cargo.toml のバージョンを "1.2.1" に更新
   CHANGELOG.md を更新
   コミット: "chore: release v1.2.1"

4. main へマージ
   git checkout main
   git merge --no-ff hotfix/v1.2.1

5. バージョンタグを打つ
   git tag v1.2.1
   git push origin main --tags

6. develop へマージバック
   git checkout develop
   git merge --no-ff hotfix/v1.2.1

7. hotfix ブランチを削除
```

## 8. CI/CD 構成

| ファイル | 実行環境 | トリガー | 内容 |
|---------|---------|---------|------|
| `.gitea/workflows/sync-github.yml` | Ubuntu (act_runner) | `push`（main / develop） | GitHub へ直接 push（フィルタ不要） |
| `.github/workflows/ci.yml` | `ubuntu-latest`（GitHub） | `push`（main / develop）/ PR | コード検証（check / test / clippy） |
| `.github/workflows/build.yml` | `windows-latest`（GitHub） | `v*` タグ push | リリースビルド・GitHub Release 作成 |

> **補足**: Gitea act_runner は DNS・Rust ツールチェーン等の問題により CI には使用しない。  
> CI は GitHub Actions（GitHub hosted runner）に一本化している。

### GitHub リリースワークフロー（Windows ビルド）

```yaml
# .github/workflows/build.yml

name: Build and Release

on:
  push:
    tags:
      - 'v*'

jobs:
  build-windows:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
        with:
          targets: x86_64-pc-windows-msvc

      - name: Build
        run: cargo build --release
        env:
          GITEA_UPDATE_TOKEN:     ${{ secrets.GITEA_UPDATE_TOKEN }}
          GITEA_UPDATE_ENDPOINT:  ${{ secrets.GITEA_UPDATE_ENDPOINT }}
          GITHUB_UPDATE_TOKEN:    ${{ secrets.GITHUB_UPDATE_TOKEN }}
          GITHUB_UPDATE_ENDPOINT: ${{ secrets.GITHUB_UPDATE_ENDPOINT }}

      - name: Package
        shell: pwsh
        run: |
          # NSIS または zip パッケージング（詳細は別途定義）

      - name: Create GitHub Release
        uses: softprops/action-gh-release@v2
        with:
          files: |
            target/release/AiPulseHub.exe
            latest.json
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

## 10. バージョン管理

### 7.1 バージョン形式

セマンティックバージョニング（`MAJOR.MINOR.PATCH`）を採用する。

| 番号 | 上げるタイミング |
|------|----------------|
| MAJOR | 破壊的変更・大規模仕様変更時 |
| MINOR | 後方互換のある機能追加時 |
| PATCH | バグ修正・軽微な改善時 |

### 7.2 バージョンの管理場所

`Cargo.toml` の `version` フィールドを**唯一の正として**管理する。

### 7.3 タグ命名規則

```
v{MAJOR}.{MINOR}.{PATCH}
例: v1.0.0 / v1.2.0 / v1.2.1
```

タグは必ず `main` ブランチのマージコミットに打つ。

| シークレット | 保管場所 | 用途 |
|------------|---------|------|
| `GITHUB_MIRROR_TOKEN` | Gitea | GitHub へのコード同期用 PAT |
| `GITEA_UPDATE_TOKEN` | Gitea / GitHub | アップデートチェック用（読み取り専用） |
| `GITEA_UPDATE_ENDPOINT` | Gitea / GitHub | Gitea の `latest.json` URL |
| `GITHUB_UPDATE_TOKEN` | GitHub | GitHub アップデートフォールバック用 PAT |
| `GITHUB_UPDATE_ENDPOINT` | GitHub | GitHub の `latest.json` URL |

## 12. コミットメッセージ規則

[Conventional Commits](https://www.conventionalcommits.org/) に準拠する。

| プレフィックス | 用途 |
|-------------|------|
| `feat:` | 新機能 |
| `fix:` | バグ修正 |
| `chore:` | ビルド・設定・バージョン変更など |
| `docs:` | ドキュメントのみの変更 |
| `refactor:` | 機能変更を伴わないリファクタリング |
| `test:` | テストの追加・修正 |

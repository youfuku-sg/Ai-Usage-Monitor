## 1. システム概要

Ai-Usage-Monitor は Windows 11 上でバックグラウンド常駐するローカルハブアプリケーション。  
Claude Code の使用量を収集・集約し、API 配信・トースト通知・タスクトレイ表示を行う。

```
[ Claude Code 認証情報 / JSONL ファイル ]
        ↓ 30秒ごとにポーリング（専用スレッド）
   [ Collector (collectors/claude.rs) ]
        ↓
   [ State Store (Arc<RwLock<AppState>>) ]
     ↓              ↓              ↓
[ axum API ]   [ Notifier ]   [ Win32 Tray ]
 Tokio ランタイム  閾値チェック    Shell_NotifyIconW
 ポート: 8765    トースト通知     コンテキストメニュー
   ↓
[ AiPulseDesk / ブラウザ 等 ]
```

## 4. スレッドモデル

```
メインスレッド
  └─ window::run() ─── Win32 メッセージループ
                         ├─ SharedState から読み取りトレイ更新
                         └─ コンテキストメニュー表示

コレクタースレッド（std::thread::spawn）
  └─ 30秒ごとに collectors::claude::poll() 実行
       └─ SharedState に書き込み → Notifier に通知

Tokio スレッド（std::thread::spawn 上で Runtime::block_on）
  └─ axum HTTP サーバー（ポート 8765）
       └─ SharedState から読み取りレスポンス生成

通知チェック
  └─ コレクター完了後に notifier::check() を呼び出し
       └─ 閾値を下回っていれば Win32 トースト通知送出
```

## 5. 設定ファイル仕様

ファイル: `config.toml`（実行ファイルと同ディレクトリ。開発時はプロジェクトルート）

```toml
[server]
host = "0.0.0.0"   # 全インターフェースでリッスン
port = 8765

[collector]
interval_sec = 30  # データ収集間隔（秒）

[notification]
# 通知する閾値（残容量%）。この値を下回った時点で通知
thresholds = [75, 50, 30, 20, 10, 5]

[updater]
enabled = true
check_interval_sec = 3600
```

設定ファイルが存在しない場合は上記デフォルト値を使用する。

## 6. データ収集仕様

### 6.1 収集方法

**プライマリ: OAuth API**

```
https://api.anthropic.com/api/oauth/usage
```

- `%USERPROFILE%\.claude\.credentials.json` から `claudeAiOauth.accessToken` を取得
- WSL 環境の認証情報も対象（`wsl.exe` 経由で読み取り）
- トークン期限切れ時は Claude CLI を呼び出してリフレッシュ（既存の `refresh_or_fallback` ロジック）
- 認証情報が存在しない場合は Claude Code を未インストールとして扱う

**フォールバック: JSONL パース**（OAuth API が失敗した場合）

```
%USERPROFILE%\.claude\projects\**\*.jsonl
```

- `type == "assistant"` かつ `message.usage` を含む行を抽出
- `message.id` で重複排除
- 過去 10 時間のエントリから 5 時間ウィンドウを計算

### 6.2 収集処理フロー

1. `config.toml` の `interval_sec`（デフォルト: 30秒）ごとに実行
2. OAuth API でデータ取得を試みる
3. 失敗した場合は JSONL パースにフォールバック
4. 計算結果を SharedState（`Arc<RwLock<AppState>>`）に書き込む
5. Notifier の閾値チェックを呼び出す

### 6.3 5時間ウィンドウ計算（JSONL フォールバック時）

```
window_start = 現在時刻 - 5時間
window_end   = 現在時刻
```

- `window_start` 以降のエントリを対象に `input_tokens + output_tokens` を合算し `tokens_used` とする
- `tokens_limit` = 88,000（暫定。将来的に `config.toml` で上書き可能にする）
- `remaining_percent = (tokens_limit - tokens_used) / tokens_limit * 100`
- `reset_at` = 直近エントリのタイムスタンプ + 5時間

## 7. State Store 仕様

`Arc<RwLock<AppState>>` でインメモリ保持し、スレッド間でスレッドセーフに読み書きする。  
`RwLock` は `std::sync::RwLock` を使用する（Tokio 非同期コンテキストで読み書きしないため）。

### 型定義（Rust）

```rust
// state.rs

#[derive(Clone, Serialize)]
pub struct ClaudeState {
    pub installed: bool,
    pub window_start: Option<DateTime<Local>>,
    pub window_end: Option<DateTime<Local>>,
    pub reset_at: Option<DateTime<Local>>,
    pub tokens_used: u64,
    pub tokens_limit: u64,
    pub remaining_percent: f64,   // 小数点第1位まで
    pub is_limited: bool,         // remaining_percent == 0 かつ現在時刻 < reset_at
    pub updated_at: DateTime<Local>,
}

pub struct AppState {
    pub claude: ClaudeState,
    pub notified_thresholds: HashSet<u8>,  // 通知済み閾値（ウィンドウリセット時クリア）
    pub start_time: Instant,               // アップタイム計算用
}

pub type SharedState = Arc<RwLock<AppState>>;
```

JSON シリアライズ時、`DateTime<Local>` は `"2026-05-18T12:34:56+09:00"` 形式（ISO 8601）とする。

## 8. API 仕様

### 8.1 共通仕様

| 項目 | 内容 |
|------|------|
| プロトコル | HTTP/1.1 |
| ホスト | `0.0.0.0`（全インターフェース） |
| ポート | `8765`（暫定） |
| レスポンス形式 | `application/json; charset=utf-8` |
| 文字コード | UTF-8 |
| タイムゾーン | ローカルタイムゾーン（JST 等）をオフセット付きで返す |

### 8.2 エンドポイント一覧

| メソッド | パス | 概要 |
|---------|------|------|
| GET | `/status` | 全監視対象の状態を返す |
| GET | `/status/claude` | Claude Code の状態のみ返す |
| GET | `/health` | サービス死活確認 |

### 8.3 `GET /status`

**レスポンス例（HTTP 200）**

```json
{
  "updated_at": "2026-05-18T12:34:56+09:00",
  "claude": {
    "installed": true,
    "window_start": "2026-05-18T07:34:56+09:00",
    "window_end": "2026-05-18T12:34:56+09:00",
    "reset_at": "2026-05-18T12:34:56+09:00",
    "tokens_used": 52000,
    "tokens_limit": 88000,
    "remaining_percent": 40.9,
    "is_limited": false,
    "updated_at": "2026-05-18T12:34:56+09:00"
  }
}
```

Claude Code が未インストール（認証情報なし）の場合:

```json
{
  "updated_at": "2026-05-18T12:34:56+09:00",
  "claude": {
    "installed": false,
    "updated_at": "2026-05-18T12:34:56+09:00"
  }
}
```

### 8.4 `GET /status/claude`

レスポンス形式は `/status` の `claude` フィールドと同一。

### 8.5 `GET /health`

**レスポンス例（HTTP 200）**

```json
{
  "status": "ok",
  "uptime_sec": 3600
}
```

### 8.6 レスポンス性能要件

- SharedState から `RwLock::read()` でキャッシュ済みデータを即返却（収集完了を待たない）
- 目標: 100ms 以内。最大: 500ms 以内

## 9. 通知仕様

### 9.1 通知手段

Win32 の `Shell_NotifyIconW`（`NIM_MODIFY` + `NIF_INFO`）でバルーン通知を送出する。  
既存の `tray_icon::notify_balloon()` を拡張して使用する。

### 9.2 閾値チェック

- コレクター処理完了ごと（30秒ごと）に `remaining_percent` を評価する
- `config.toml` の `thresholds` に定義された各閾値を下回った場合に通知を送出する

### 9.3 重複防止

- 各閾値の通知済みフラグを `AppState.notified_thresholds` に保持する
- `window_start` が更新された（＝新しいウィンドウに移行した）タイミングで全フラグをリセットする

### 9.4 通知内容

| 項目 | 内容 |
|------|------|
| タイトル | `Ai-Usage-Monitor` |
| 本文1行目 | `Claude Code 残容量が {閾値}% を下回りました` |
| 本文2行目 | `現在の残容量: {remaining_percent:.1f}%` |
| 本文3行目 | `リセット予定: {reset_at を "HH:MM" 形式で表示}` |

## 11. 起動・終了仕様

### 11.1 起動シーケンス

1. `config.toml` を読み込み `AppConfig` を構築（存在しない場合はデフォルト値）
2. `AppState` を初期化し `SharedState`（`Arc<RwLock<AppState>>`）を生成
3. Tokio スレッドを `std::thread::spawn` で起動し、内部で axum HTTP サーバーを起動
4. コレクタースレッドを `std::thread::spawn` で起動
5. `config.toml` の `updater.enabled` が `true` の場合、アップデートチェックスレッドを起動
6. Win32 トレイアイコンを登録
7. Win32 メッセージループに入る（`window::run()`）

### 11.2 終了シーケンス

1. 右クリックメニュー「終了」でメッセージループを終了
2. Tokio スレッドに `CancellationToken` または `oneshot` チャンネルで停止シグナルを送信
3. コレクタースレッドはアトミックフラグで停止
4. トレイアイコンを削除（`Shell_NotifyIconW(NIM_DELETE, ...)`）
5. プロセス終了

## 12. エラーハンドリング方針

| エラー種別 | 対処 |
|-----------|------|
| OAuth API 認証エラー | JSONL フォールバックに切り替え。`eprintln!` でログ出力 |
| JSONL パースエラー（1行） | その行をスキップし処理継続 |
| JSONL ファイル読み込みエラー | そのファイルをスキップし処理継続 |
| コレクタースレッドパニック | `std::thread::spawn` の `JoinHandle` でキャッチし再起動 |
| axum サーバー起動失敗（ポート使用中等） | トースト通知を送出し、API なしで起動継続 |
| 通知送出失敗 | ログに記録し処理継続（通知失敗で監視が止まらないこと） |

ログは `eprintln!` でコンソールに出力する（初期バージョン）。  
Release ビルドではコンソール非表示のため、将来的に `tracing` + ファイル出力を追加する。

## 14. 自動アップデート仕様

### 14.1 概要

既存の `updater.rs` をベースに、Gitea 優先・GitHub フォールバック方式に改修する。

```
アップデートチェック開始（起動 60 秒後・以降 1 時間ごと）
  │
  ├─ ① Gitea エンドポイントへリクエスト
  │     ├─ 成功 → バージョン比較 → 必要なら Gitea からダウンロード
  │     └─ 失敗 → ② GitHub エンドポイントへリクエスト
  │                   ├─ 成功 → バージョン比較 → GitHub からダウンロード
  │                   └─ 失敗 → ログ記録・スキップ
  │
  ダウンロード完了 → トースト通知 → ユーザー承認 → インストーラ実行
```

### 14.2 機能要求

**REQ-UPDATE-001**: 起動後 60 秒・以降 `check_interval_sec` ごとにアップデートチェックを実行できること

**REQ-UPDATE-002**: 新バージョン検出時、バックグラウンドで差分ファイルをダウンロードできること

**REQ-UPDATE-003**: ダウンロード完了後、トースト通知でユーザーに通知し、クリックでインストーラを実行できること

**REQ-UPDATE-004**: `config.toml` の `updater.enabled` で自動アップデートの有効・無効を切り替えられること

**REQ-UPDATE-005**: チェック失敗時はログに記録して次回まで待機し、エラー扱いにしないこと

### 14.3 エンドポイント設定（ビルド時埋め込み）

```rust
// build.rs でビルド時に環境変数から埋め込む
const GITEA_UPDATE_ENDPOINT: &str = env!("GITEA_UPDATE_ENDPOINT");
const GITEA_UPDATE_TOKEN:    &str = env!("GITEA_UPDATE_TOKEN");
const GITHUB_UPDATE_ENDPOINT: &str = env!("GITHUB_UPDATE_ENDPOINT");
const GITHUB_UPDATE_TOKEN:    &str = env!("GITHUB_UPDATE_TOKEN");
```

### 14.4 アップデートチェック用 JSON（`latest.json`）

```json
{
  "version": "1.0.1",
  "notes": "バグ修正・機能改善",
  "pub_date": "2026-05-18T00:00:00Z",
  "url": "https://{ホスト}/{owner}/Ai-Usage-Monitor/releases/download/v1.0.1/Ai-Usage-Monitor_1.0.1_x64-setup.exe",
  "signature": "<署名（将来対応）>"
}
```

### 14.5 バージョン管理

- 形式: セマンティックバージョニング（`MAJOR.MINOR.PATCH`）
- 管理場所: `Cargo.toml` の `version` フィールド
- タグ形式: `v{MAJOR}.{MINOR}.{PATCH}`

## 15. CI/CD 仕様

### 15.1 リポジトリ役割分担

| リポジトリ | 役割 | コミット対象 |
|-----------|------|------------|
| **Gitea** | 全データ保管庫・開発の中心 | コード・ドキュメント・全ファイル |
| **GitHub** | CI/CD・リリース専用 | コードのみ（`docs/` 等を除く） |

Gitea へのプッシュを起点に、Gitea Actions が `docs/` を除いたコードのみを GitHub へ同期する。  
リリースビルドは GitHub Actions（`windows-latest`）でのみ行う。

### 15.2 ワークフロー構成

| ファイル | 実行環境 | トリガー | 内容 |
|---------|---------|---------|------|
| `.gitea/workflows/ci.yml` | Ubuntu (act_runner) | push / PR | `cargo check` / `test` / `clippy` |
| `.gitea/workflows/sync-github.yml` | Ubuntu (act_runner) | main / develop への push | `docs/` 除外して GitHub へ同期 |
| `.github/workflows/build.yml` | `windows-latest` | `v*` タグ push（同期経由） | `cargo build --release` → パッケージング → リリース作成 |

### 15.3 成果物

| ファイル | 内容 |
|---------|------|
| `Ai-Usage-Monitor_{version}_x64.exe` | インストーラ（手動インストール用） |
| `Ai-Usage-Monitor_{version}_x64.zip` | 自動アップデート用アーカイブ |

## 16. 将来拡張の考慮

- `collectors/` にファイルを追加するだけで新しい監視対象を追加できる構造とする
- `api/` に対応するルーターファイルを追加することで個別エンドポイントを拡張できる構造とする
- Web ダッシュボードの要否が確定した時点で Tauri 移行を再検討する
- Tauri 移行時は `SharedState` の型定義・コレクター・通知ロジックをそのまま移植できるよう、Win32 固有の処理を `tray_icon.rs` / `native_interop.rs` に閉じ込める

## 17. 用語定義

| 用語 | 定義 |
|------|------|
| State Store | 収集済みデータをインメモリで保持する中間ストレージ（`Arc<RwLock<AppState>>`） |
| Collector | データ収集・パースを担うモジュール |
| SharedState | `Arc<RwLock<AppState>>` の型エイリアス。スレッド間でデータを共有する |
| 5時間ウィンドウ | Claude Code のレート制限の計算基準となる直近5時間の区間 |
| 残容量 | `(tokens_limit - tokens_used) / tokens_limit × 100`（%） |
